NOTES, ASSUMPTIONS AND TRADEOFFS
================================

NOTES / OPEN ISSUES
-------------------

1. Airport-count cap vs. the New England question (conflicts with task.md)

   task.md's first example question is "Which airports in New England are strong candidates
   for terminal expansion?". system_prompt.py tells the agent not to query more than 10
   airports per request, and to decline if a request needs more.

   The data has 38 large/medium airports across the six New England states (US-ME, US-NH,
   US-VT, US-MA, US-RI, US-CT). So as written, the agent will decline the first task question.

   Why the cap exists: each get_congestion_level call fetches departures and arrivals for
   every day in the window (3 days by default), which is 6 OpenSky requests per airport on a
   cold cache. 38 airports is about 228 requests, which risks OpenSky rate limits and a very
   slow answer.

   Options (undecided):
   - Add the OurAirports `type` (large_airport / medium_airport) to the Airport model, so the
     agent can narrow to large airports first. Most New England airports are medium.
   - Pre-filter candidates cheaply by runway count before fetching any flights.
   - Move ranking into a deterministic tool that scores the whole region server-side. This
     would also strengthen task.md's "deterministic scoring or ranking logic" requirement.
   - Raise the cap, and accept slower answers and rate-limit risk.


ASSUMPTIONS
-----------

1. Passengers: all flights are full - no way to figure out passengers. The analysis is
   flight-based (movements), not passenger-based.

2. Scope: US large and medium airports from OurAirports. Small airports, heliports and
   seaplane bases are excluded.

3. Regions are single US states (ISO 3166-2 codes such as "US-MA"). Informal groupings like
   "New England" are treated as a list of states.

4. Capacity = open runways x 20 flights per runway per hour. Closed runways and helipads are
   excluded. This ignores runway configuration (parallel vs. crossing), weather, ATC
   procedures, gates and terminal size.

5. Practical capacity = 85% of theoretical capacity - the realistic sustainable ceiling.

6. Utilization is measured at peak, not on average: the top 3 busiest hours of each day,
   averaged over the window, divided by capacity. Congestion is a peak-hour problem, so an
   all-day average would hide it.

7. Congestion bands (by utilization %): below 50 low, 50-80 moderate, 80-100 high, above 100
   over capacity. "unknown" when the airport has 0 runways in the data.

8. Time window: the last 3 full UTC days, ending at today's UTC midnight. Flights are bucketed
   by UTC hour, so a "day" starts at UTC midnight, not local midnight. Hours and days with no
   flights count as 0.

9. Flight data: OpenSky ADS-B coverage is incomplete, so flight counts are a lower bound on
   real traffic.

10. Long-haul = a flight longer than 5 hours, measured from OpenSky's firstSeen/lastSeen
    timestamps. Coverage gaps (e.g. over oceans) shorten measured durations, so long-haul
    counts are a lower bound too.

11. Unmet demand can't be observed directly - flights that didn't happen aren't in any data.
    The proxy is observed peak traffic compared with practical and theoretical capacity.

12. Terminal expansion candidates are judged by runway-side congestion. There is no terminal,
    gate or passenger-processing data, so a busy runway system stands in for a busy terminal.


TRADEOFFS
---------

1. The deterministic layer measures, the agent reasons. Python computes the counts,
   utilization and congestion levels; the LLM ranks, compares and computes percentages
   (e.g. long-haul share) from them.
   + Flexible, and the agent can explain its reasoning in the answer.
   - Rankings are not fully deterministic, which weakens task.md's "deterministic scoring or
     ranking logic" requirement (see note 1).

2. OpenSky for flight data.
   + Recent, per-flight movement data with timestamps, free.
   - Rate-limited, historical only (no same-day data), and coverage gaps undercount traffic.
     No passenger counts.

3. Local cache per airport, direction and UTC day (data/flights/*.json), and a daily refresh
   for the OurAirports CSVs.
   + Repeat questions are fast and don't spend OpenSky quota.
   - Invalidated by date only: a schema or logic change needs the cache deleted by hand.

4. All tunable numbers live in settings.yaml (capacity per runway, window, peak hours,
   congestion bands, long-haul threshold, practical capacity %, model).
   + Assumptions are easy to find, change and explain.
   - The assumption text in reports is partly hardcoded, so it can drift from the settings.

5. Tools exposed through a separate MCP server rather than plain Python functions.
   + A clean boundary between data/analytics and the agent; any MCP client can reuse the
     tools.
   - An extra subprocess, and more moving parts than calling functions directly.

6. Manual tool-call loop instead of the Gemini SDK's automatic function calling.
   + Works around a google-genai bug (it deep-copies the config, which crashes on a live MCP
     session), and gives full visibility of each call for the UI's tool-calls panel.
   - More code to own (the loop, error handling, result formatting).

7. Tool results are full reports, and one flights call returns both directions plus the
   long-haul count.
   + Fewer LLM round trips, and the agent always has the assumptions and inputs behind a
     number.
   - Larger payloads per call (more tokens).

8. A fresh MCP connection per chat turn in the Streamlit UI, with Gemini's chat history
   carried between turns in st.session_state.
   + Simple and robust with Streamlit's rerun-the-whole-script model.
   - A small overhead each turn (subprocess start and tool listing).

9. Model: gemini-3.5-flash-lite instead of gemini-3.8-flash.
   + Far fewer 503 "high demand" errors on the free tier; faster.
   - Weaker reasoning than the larger model.

10. Retry on 429/503 (3 attempts with backoff).
    + Rides out short free-tier spikes.
    - A slow answer when the API is struggling, instead of failing fast.

11. A 10-airport cap per request (system prompt).
    + Protects the OpenSky rate limit and keeps answers reasonably fast.
    - Blocks region-wide questions such as New England (see note 1).

12. mcp pinned below 2.0.
    + Keeps the simple, widely documented FastMCP API.
    - Not on the newest MCP SDK.
